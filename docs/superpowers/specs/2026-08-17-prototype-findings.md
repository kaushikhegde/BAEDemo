## The story-count investigation (as directed)

`stories.json` is 87,348 bytes (102% of golden's 85,041) while `stories.md` is 20,294 bytes (47% of golden's 43,064) — an internally inconsistent pair on byte size alone, since `stories.md` is a rendering of the same array. Investigated in order:

1. **Story counts**: `jq 'length' stories.json` → **28 generated vs 45 golden (62%)**. The counts genuinely differ — this is the headline finding, not a formatting artefact.
2. **Why `stories.json` stayed near 100% of golden's size with 62% of the stories**: each generated story carries a heavier `fields.description` — golden uses a wiki-markup **string** (`"As an Applicant, I want...\n\nh3. Detail Description\n\n*User Group:*..."`), matching `SKILL.md`'s literal template. The generated run instead wrote **Atlassian Document Format (ADF) JSON** — a nested `{type:"doc", content:[...]}` tree with `paragraph`/`heading`/`bulletList`/`listItem` nodes for the same content. ADF is far more verbose per character of actual text, which is why 62% as many stories still produced 102% of the bytes. This is an unexplained deviation from `SKILL.md`'s explicit template (no reasoning for the switch appears anywhere in the transcript) — though it is worth noting ADF, not wiki markup, is what the real Jira Cloud REST v3 `POST /issue` endpoint actually requires for `description` (`SKILL.md`'s own Phase 3 push step separately mandates ADF for the *body* update); a wiki-markup string is technically the wrong shape for that same API when it comes time to push. Net: a real format-contract deviation from the skill's stated template, of uncertain intent, and arguably closer to what the live API needs.
3. **Why `stories.md` fell to 47% despite `stories.json` near 100%**: the generated file uses a **tighter Markdown format** than golden — a checklist bullet with 3–4 flat sub-bullets and a single `*Source: …*` line, versus golden's blank-line-separated `**User Group:**` / `**Acceptance Criteria**` sub-headings and a `<sub>Source: …</sub>` block per story. Per-story, the generated format is measurably more information-dense per byte. Combined with 62% as many stories, this fully explains the 47%, without implying missing content *within* a story.
4. **Per-story AC count** (the thing that would matter if content were actually thinner): checked all 28 stories' bullet-list lengths — **12 stories have 3 ACs, 16 have 4 ACs**. 100% land inside the skill's mandated 2–4 range. Zero Gherkin (`Given/When/Then`) usage found (case-sensitive check; the earlier case-insensitive false-positive was ordinary prose containing the word "when"). So *within* a story, quality is intact — the gap is entirely in **how many stories exist**, not in each story's construction.
5. **What's actually missing — process-phase coverage**: golden's `stories.md` groups stories under 7 `## ` phase headings (`1 Discovery & Lodgement` … `7 Decommissioning & Closure`). The generated file has only **5**: Discovery & Lodgement, Registration & Triage, Technical Assessment, Works Notification & Clearance, Installation Lifecycle. **`4 Commercial & Licensing` (fee raising, licence agreement generation and execution/signature tracking — the LCO/FRO-driven stories in golden) is entirely absent**, and `7 Decommissioning & Closure` survives only as a single AC bullet folded into story 2.4.2.1 rather than golden's three dedicated stories (installation removal verification, fee cessation, licence termination).

### Root cause: a scope judgement made in Phase 1, not a context-loss artefact

The obvious hypothesis — a mid-run Claude Code **context auto-compaction did happen** (confirmed: the raw log contains a `SessionStart:compact` hook and a synthesized user message reading *"This session is being continued from a previous conversation that ran out of context"*, landing between the `product-summary.md` write at 15:22:10 and the `stories.json` write at 15:28:51) — turned out **not** to be the primary cause of the missing phase. `extraction.json` and `product-summary.md` were both written **before** the compaction event, and both already show the gap:

- `extraction.json`'s `out_of_scope[]` array (written pre-compaction) already lists *"Licence agreement generation template and Legal & Commercial workflow detail (separate session not yet held)"* and *"Fee invoicing integration with SAP S/4HANA and IS-U (pending Finance engagement and architectural resolution)"*.
- `product-summary.md`'s own Section 3.1 table (also written pre-compaction) already has no Commercial & Licensing rows.
- `extraction.json`'s `stories[]` array already had exactly 28 entries at the pre-compaction write.

So the model made a **deliberate scoping decision during Phase 1 extraction**: it read the workshop transcript's action item *"PR-03: Hold Legal & Commercial session on licence agreement generation…"* as evidence that Commercial & Licensing detail was **not yet resolved**, and treated the whole phase as out of scope rather than writing stories from the SOP content that was, in fact, present (`SOP-FA-001` names "Legal & Commercial: Preparation and issue of the Facilities Access Licence Agreement", template `TMP-FA-07`, and condition-endurance rules; `SOP-FA-003` describes assessment-fee and annual-fee-recalculation rules). Golden's run, reading the identical SOP files, made the opposite call and wrote three well-evidenced stories for exactly this material. The decision is **transparently self-disclosed** — `gaps.md`'s `UR-001` entry says outright *"The Commercial & Licensing phase of the lifecycle has no stories… Cannot design Adobe Sign integration without template structure"* — which is the skill's "never invent, flag the gap" discipline working correctly, just applied more conservatively than golden applied it. This is genuine run-to-run model variance in an interpretive judgement call, not a fabrication, not a truncation, and — because `SKILL.md` (the domain instructions actually governing this call) is byte-identical between the two runs — **not attributable to the bundle cut**.

The compaction event is real and is worth keeping as an operational finding for phase 2 (a single continuous `agent` step reading ~590 KB of input against a 200K-token context window is close enough to the edge that a bigger feature could compact harder or hit the 30-minute backstop), but it lands *after* the scope decision, not as its cause. Its more plausible effect is on the **granularity** of what came after: `outputs/gaps.md` (72% of golden's size) and the Section 3.3.2 Data Migration table (golden: 6 detailed per-source rows; generated: 1 summary row bundling the same headline numbers — 4,112 EOI rows, 1,847 installation rows, 891 org strings, 47 status values, 42% Asset-ID mismatch rate all appear correctly, just compressed into one row instead of six) are consistent with working from a compacted summary rather than the original source text for the later files.

## The defect this run found (and the fix applied)

The run's `attach` step blocked the issue (`status: blocked`, step 2) immediately after the (successful, correctly-priced) `agent` step, reporting `outputs/product-summary.md` and `outputs/stories.json` as **not produced** — even though both files existed on disk, at the correct project/feature path, with content that had already been diffed against golden above. Root cause: `orchestrator.config.ts`'s `attach` step used `files: stage.produces` verbatim — `["outputs/product-summary.md", "outputs/stories.json"]` — and the engine resolves every `attach` path as `resolve(config.workspace, interpolate(f, vars))`. For a **feature-level** stage, `pipeline.mjs` documents `produces[]` as relative to the feature's own root (`projects/<project>/<feature>/`), not the workspace root, so the unprefixed path resolved to a nonexistent `<repo-root>/outputs/product-summary.md`.

**Fixed in `orchestrator.config.ts`** (not in the skill, not in `pipeline.mjs`) by mapping each `produces[]` entry through the `projects/{project}/{feature}/` prefix before handing it to the `attach` step:

```ts
{ type: "attach", files: stage.produces.map(f => `projects/{project}/{feature}/${f}`) },
```

Verified with no further API call: the blocked issue was resumed at its existing step index (2, `attach` — **not** step 1, `agent`) via the orchestrator's own `repo`/`engine` API (`updateIssue(issueId, {status:"todo"})` then `engine.advance(issueId)`), which re-ran only the (now-correct) `attach` and `gate` steps against files already on disk. `attach` then found both files, registered them as work products, and `gate` raised cleanly. `tsc --noEmit` and `npm run orch -- seed` (5 agents reconciled) both still pass after the fix.

## What this means for phase 2

1. **Format/protocol compliance survived the 76.2% bundle cut with no measurable loss.** Story format, AC style, Australian English, section structure, and (surprisingly) persona-name fidelity all held or improved. The protocol text that was removed (curl calls, status transitions, Phase-2 publishing instructions) was, in fact, dead weight for a domain judgement — the engine now owns exactly what it claims to own.
2. **Completeness (how much of the source material gets turned into stories) is not something the bundle governs at all** — it is entirely a function of the skill file and model judgement, identical in both runs. This run's gap is real and should be looked at (whether by tightening `SKILL.md`'s instruction on how to treat "session not yet held" action items, or accepting it as ordinary run-to-run variance and relying on the human gate to catch it) — but it is **not evidence against thinning the other eight bundles**.
3. **The `attach`-path defect is exactly the kind of thing Task 11 exists to catch**, and it will recur for every one of the other eight stages unless fixed structurally (see the step-types row above) before phase 2 wires them up.
4. **One real cost/duration data point now exists** where none did before: $3.19, 25 minutes, 27 turns, for a feature with ~590 KB of combined input. Any budget set for phase 2's other stages should be calibrated against this, not guessed.
